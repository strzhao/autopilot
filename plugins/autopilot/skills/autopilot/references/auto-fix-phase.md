# Phase: auto-fix — 详细工作流

## 红队测试铁律
**默认不允许修改红队验收测试**——问题在实现，不在测试。唯一例外：明确属红队测试本身问题（三情形见 §6「红队测试例外与重锁流程」），按双层决策树分流：证据链闭合（E1-E3）→ AI 自决改测试 + 重锁 + 变更日志留痕，无需打断用户；证据链不闭合（U1-U4）→ `AskUserQuestion` 升级人工定夺。

> 防合理化借口对照见 references/anti-rationalization.md（auto-fix 阶段段）。

## 1. 读取失败项
从最近一轮 QA 报告中提取所有 ❌ 标记的项目。

## 2. 区分失败来源并确定修复策略

**并行判断**：如果多个失败项涉及**不同文件且互不依赖**，可以并行修复（多个 Edit 调用）。涉及**同一文件或有依赖关系**时必须串行。

### 红队验收测试失败（Tier 0）— 最高优先级
- **含义**：实现不符合设计要求
- **修复目标**：修改实现代码使其满足设计文档的要求
- 修改红队测试文件（`.acceptance.test.*`）：仅铁律例外三情形允许——证据链闭合 AI 自决 + 重锁 + 留痕，证据不足才 `AskUserQuestion` 升级（见 §6）
- **修复方式**：
  1. 阅读失败的验收测试，理解它期望的行为
  2. 对照设计文档确认期望是正确的
  3. 定位实现代码中的偏差
  4. 修改实现代码以满足期望

### 蓝队单元测试失败（Tier 1 测试部分）
- **含义**：实现内部有 bug
- **修复方式**：修复实现代码中的 bug
- **特殊情况**：如果蓝队测试与红队测试矛盾（测试同一行为但期望不同），以红队测试（设计意图）为准，修改蓝队测试

### 类型/Lint/构建失败（Tier 1 其他部分）
- 类型错误 → 修正类型声明或实现
- Lint 错误 → `eslint --fix` 或手动修复
- 构建失败 → 检查导入、依赖、配置

### 代码质量/安全问题（Tier 2-4）
- 最小化重构，保持行为不变

### 真实场景验证失败（Tier 1.5）
- **含义**：功能在真实用户场景下不可用（可能单元测试全通过但真实运行失败）
- **修复方式**：
  1. 分析场景执行的实际输出（错误信息、日志、退出码）
  2. 与预期结果对比，定位偏差点
  3. 这类问题通常是集成问题（路径、环境、权限、配置），而非逻辑错误
  4. 修复后必须重新执行该场景验证，附上成功输出作为证据

## 3. 统一修复 — 批量调试方法论

全部失败项统一走两段式流程，禁止修一项验一项：

**阶段一 · 逐项分析（不改代码）**——对每个失败项严格按三阶段执行：**观察**：完整阅读错误信息与堆栈，不跳过任何细节。**假设**：形成明确因果假设「X 导致 Y，因为 Z」，写下再行动。**验证**：用最小实验验证（加日志 / 单跑一个测试 / 查变量值），假设被推翻 → 回到观察，不在错误假设上继续修。
分析完成后做**共同上游根因分析**：看似独立的失败优先找共同上游脆弱点，一个根因可能解释多个失败项。

**阶段二 · 统一修复 + 一轮验证**——假设被验证后才动手：统一修复全部失败项（互不依赖可并行 Edit，同一文件有依赖则串行）→ `git add` 暂存 → **一轮**跑齐所有失败项对应检查命令（同一命令只跑一次），输出作证据。触及任何测试文件 → 作废 state.md `## 蓝队自检` 区域。

## 4. 重试控制
- 读取 frontmatter 的 `retry_count`
- `retry_count++`，更新状态文件
- **retry_count < max_retries** → 设置 `qa_scope: "selective"`，更新 `phase: "qa"` 回去选择性重跑失败 Tier
  - 例外：如果本次 auto-fix 是从 Wave 1 快速路径进入的（QA 报告标注了 `[快速路径]`），不设置 `qa_scope`，执行全量 QA
- **retry_count >= max_retries** → 停止自动修复：
  - 在 QA 报告中标注哪些已修复、哪些仍未解决
  - 更新 `gate: "review-accept"`（让用户决定）

## 5. 修复优先级
1. 红队验收测试失败（Tier 0）→ 实现不符合设计，必须修复实现
2. 真实场景验证失败（Tier 1.5）→ 功能在用户场景下不可用
3. lint/类型错误 → 通常可自动修复
4. 蓝队单元测试失败 → 分析是实现 bug 还是测试本身问题
5. 构建失败 → 检查导入、依赖、配置
6. 安全问题 → 添加输入验证、转义、权限检查
7. 代码质量问题 → 重构，保持最小改动

## 6. 红队测试例外与重锁流程

铁律默认不改红队测试。**唯一例外**：失败项明确属红队测试本身问题（三情形），按**双层决策树**分流——证据链闭合 AI 自决，不闭合才升级用户。

**三情形**（之外一律不改，问题在实现）：
1. 断言与契约矛盾——断言期望与 `## 契约规约`/`## 验收场景` 的明确表述相反（**须附 design 字段 vs test 期望的字段级 diff 证据**，防合理化）。
2. 测试引用设计文档未声明的私有 seam（注入点在设计与实现中均不存在）。
3. 断言机制错（grep 命中注释/反语序、硬编码计数如 `count==5` 未随扩展同步）。

### 双层决策树（Tier 0 失败时）

```
红队测试失败 → 根因分类
├─ 实现 bug（三情形之外）→ 修实现（默认路径，不变）
└─ 红队测试自身问题（三情形之一）
   ├─ 证据链闭合（E1-E3 任一成立）→ AI 自决：改测试 + 重锁 + 留痕，无需打断用户
   └─ 证据链不闭合（U1-U4 任一命中）→ `AskUserQuestion` 升级人工定夺
```

**证据链闭合判据（E1-E3，命令输出可直接指认）**：
- **E1（情形①）**：`## 契约规约`/`## 验收场景` 中存在与断言期望字面相反的明确表述，能写出字段级 diff（design 字段 vs test 期望逐字对照）。
- **E2（情形②）**：grep 设计文档 + 实现代码均无该接口/成员声明，grep 命令与零命中输出作证据。
- **E3（情形③）**：错误机制可被命令输出直接指认（如 `grep -n` 显示断言命中注释行/反语序；计数断言与契约措辞矛盾对照）。

**升级情形（证据不足 / 边缘情形，走 `AskUserQuestion` 人工定夺）**：
- **U1 契约歧义/沉默**：设计文档未写清楚期望行为——改测试没有逐字锚点，属 design 缺陷须人工定夺。
- **U2 谓词 SSOT 冲突**：断言与 `## 验收场景` 预注册谓词矛盾且谓词本身疑似错——谓词是全链路冻结 SSOT，影响下游 plan-reviewer/QA，不得单方动。
- **U3 根因无法机械指认**：无法用 E1-E3 产出命令级证据，多情形混杂。
- **U4 覆盖语义变化**：需要删测试用例、放宽断言、或修改后断言无法从契约文本逐字推导。

### 自决路径（证据链闭合）

改测试 → **重锁放行**（解 §8.5.1 tamper 守卫）：

```bash
# lock_acceptance_tests 是 lib.sh 的 source 函数（非 CLI），须 source 后调
source plugins/autopilot/scripts/lib.sh && lock_acceptance_tests "$TASK_DIR/.acceptance-lock" <改动测试文件绝对路径>
```

重锁覆盖 `.acceptance-lock` 旧 SHA → 下次 implement→qa §8.5.1 检测匹配 → 放行（**§8.5.1 检测逻辑不动**）。重锁前确认 `$TASK_DIR/acceptance-staging/manifest` 已清空或不存在（防 §8.5.0.5 合流覆盖重锁）。

**防放水锚点**（对铁律不弱化的部分）：
1. **逐字一致**：修改后的断言必须能从 `## 契约规约`/`## 验收场景` 文本**逐字推导**——即「红队当初写对时会写出的测试」。只许修正为契约一致，禁止放宽要求（见 references/contract-protocol.md 契约逐字一致原则）。
2. **三情形闭集不变**：三类之外一律不改测试——问题在实现，避免"测试放水给虚假 PASS"。
3. **证据硬前置 + hook backstop**：变更日志留痕必须附 E1/E2/E3 证据，无证据的自决 = 放水（见 references/anti-rationalization.md auto-fix 段）；stop-hook §8.5.1b 留痕守卫机械兜底——已锁测试文件有 diff ∧ 变更日志无留痕 → block。

**留痕（自决改测试的强制动作）**：在状态文件 `## 变更日志` 记一行：

`[auto-fix] AI 自决改红队测试 <文件>，情形<①②③>，证据<E1/E2/E3 关键输出>，已重锁`

**QA 报告区块转记**：下一轮 QA 报告须含「红队测试修改清单」区块（编排器从变更日志转记），用户 merge 前可审计可回滚。
