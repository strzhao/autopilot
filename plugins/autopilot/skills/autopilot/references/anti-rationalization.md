# 防合理化指南（Anti-Rationalization）

> AI 在跳过验证 / 重写测试 / 缩减红队 时常见的自我合理化借口及对应的真相。
> 仅在你想跳过测试 / 重做 / 简化流程时阅读。

## implement 阶段

红蓝对抗模式下，蓝队最常想绕过红队独立验证：

| 借口 | 现实 |
|------|------|
| 太简单 / 先实现再补 | 简单改动也出 bug；后补测试不验证需求 |
| 时间紧跳过 TDD / 红队没必要 | TDD 比 debug 快；自测 = 偏差验偏差 |
| 多跑几轮测试更稳妥 / 真实场景不验不放心 | 编译期自检通过即可交付；真实场景验证是 QA Tier 1.5 独立职责，蓝队重做 = 串行越界耗时 |
| 测试挂死了得查清楚 / 看起来快修好了 | 挂死若是既有 flaky / 运行时问题（与本次改动无关）→ 标 `[!]` 交 QA；蓝队无限 retry 是 72min 死循环根因 |
| 冒烟发现个小问题顺手修了 | 顺手修 = 范围漂移（规则7）；非计划改动交 QA 统一处理 |

要点：信息隔离不是"流程负担"，是测试独立性的保证。红队只看设计文档，蓝队只看实现。打破隔离 = 测试退化为「测我已写的」。

## implement 阶段（红队 Agent 视角）

红队最常见的合理化是给"未实现的功能"留容错空间，但这恰好掩盖了回归：

| 借口 | 现实 |
|------|------|
| 蓝队还没产出 → 加 if/else 保护 | 红测试本应失败；TDD 的红是设计意图 |
| console.warn 比 assert.fail 友好 | warn 不挂 CI = 没断言 |
| 路由可能未实现 → 接受 404 | 设计文档说必须有就必须是 200 |
| 多端协议字段不确定 → 写宽松断言 | 设计文档没声明的不该出现，声明的必须存在 |

要点：红队测试 = 设计契约的代码化。容错代码属于实现，不属于测试。失败的红队测试是 TDD 的核心信号，不要把它修成 PASS。

## qa Tier 1.5 真实场景验证

QA 阶段最常见的偷懒是用单元测试结果替代真实场景验证：

| 借口 | 现实 |
|------|------|
| dev server 太重 / 已通过 tsc+jest | `npm run dev &` 等 5 秒即可；单测验证代码结构，真实测试验证用户场景 |
| 设计文档没写 / 后续手动验证 | 没有就自行设计 1 个；QA 阶段就是验证阶段，"后面再验"= 跳过验证 |
| 蓝队已冒烟 / 场景 1 已验核心 | QA 必须独立执行；little-bee-cli 48 测全过但 4 bug 靠手动发现，只跑了 --help |

要点：Tier 1.5 是「功能在真实用户场景下是否可用」，不是「代码是否正确」。每个场景必须有 `执行:` 命令 + `输出:` 真实输出。

## auto-fix 阶段

自动修复阶段最危险的合理化是**无证据放水**：改红队测试凑 PASS 或盲目改代码：

| 借口 | 现实 |
|------|------|
| 改断言值就过了 / 我知道问题直接修 | 铁律默认禁改红队测试；例外走 §6 双层决策树：证据链闭合 AI 自决 + 重锁 + 留痕，证据不足才 AskUserQuestion 升级；70% shotgun fix 引入新 bug，先验证假设再修 |
| 无证据 / 证据不足就自决改测试 | 无证据的自决 = 放水：E1-E3 证据不闭合就走 AskUserQuestion 升级；stop-hook §8.5.1b 留痕守卫机械拦截「改测试不留痕」 |
| 蓝队自检可沿用 → 多沿用几项 / 近似命令也算同 | 沿用判定不得扩大化：语义等价从严（同套件子集可沿用；缺项/近似不同命令一律重跑），三条件缺一重跑 |

要点：红队验收测试代表设计意图，失败 = 实现不符合设计，默认修实现而不是改测试；仅明确属红队测试本身问题（三情形）时按 §6 双层决策树处理——证据链闭合才 AI 自决改测试（留痕 + 重锁），证据不足走 AskUserQuestion 升级。修复前必须走「观察 → 假设 → 验证 → 修复」四步法。
